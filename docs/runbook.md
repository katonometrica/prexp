# Runbook

How to run Prescription Explorer in production: what is where, the routine jobs, and what to do when something goes wrong. [docs/server.md](server.md) sets the server up; this page operates it. Private values (Coolify's address, ids, passwords and tokens) never appear here: they are `<coolify-host>`, `<db-id>`, `<app-id>` and `<jobs-id>`, as in server.md. The app's address is public: `<app-host>` below is [prexp.katonometrica.com](https://prexp.katonometrica.com/).

## The parts

| Part | What it is | Where |
| --- | --- | --- |
| The database | PostgreSQL 18, the image pinned by digest, with `docker/db/postgresql.prod.conf`. Private: no published port | Coolify: the `prexp` project, `prexp-db` |
| The `jobs` container | The app image, sleeping under an init. Migrations, loads and checks run in it, as Coolify's post-deployment command and scheduled tasks, or by hand in its Terminal | `prexp-jobs` |
| The app | The app image, at `https://<app-host>`, behind Coolify's proxy, with a health check on `/` and `X-Robots-Tag: noindex, nofollow` | `prexp-app` |
| The images | `ghcr.io/katonometrica/prexp-app`, `:main` and `:<commit sha>`, public | GitHub packages |
| Deploys | CI's `app-publish` job, after each merge to `main` | `.github/workflows/ci.yaml` |
| Alerts | Coolify emails a failed scheduled task or deployment | Coolify: Notifications |

**Where the credentials live** (never their values):
- **The three roles' passwords** (`PREXP_OWNER_PASSWORD`, `PREXP_LOADER_PASSWORD`, `PREXP_APP_PASSWORD`): in each resource's Environment Variables in Coolify. `prexp-db` has all three (its initialization scripts read them once), `prexp-jobs` the owner's and the loader's, and `prexp-app` the app's only.
- **The `postgres` superuser's password:** generated by Coolify, on `prexp-db`'s General page. Nothing in prexp uses it: the repairs below run `psql -U postgres` in `prexp-db`'s Terminal, over the container's socket, which asks for no password. It protects the superuser's logins over prexp's network.
- **CI's deploy token and Coolify's address and ids:** the repository's Actions secrets `COOLIFY_TOKEN`, `COOLIFY_HOST`, `COOLIFY_APP_UUID` and `COOLIFY_JOBS_UUID`. The token is a Coolify API token with the Deploy permission only, for the two applications, and expires after a year.

## Routine

| When (server time, UTC) | Task (`prexp-jobs` → Scheduled Tasks) | Command |
| --- | --- | --- |
| 02:00 on days 18 to 28 | Monthly load | `timeout 3h Rscript -e "prexp::load_latest()"` |
| 04:00 every day | Nightly check | `Rscript -e "prexp::migrate(); prexp::check_plans(max_ms = 150)"` |

- **The monthly load** loads the newest published month not yet loaded, which drops the oldest, and reloads any loaded month the portal has published again. With nothing new it logs "Nothing to load" and exits 0. NHSBSA publishes each month around the 20th, two months after the month it covers ([docs/dataset.md](dataset.md)), so most of those runs find nothing. A month takes about five minutes on the server.
- **The nightly check** applies any new migration and runs the 25 query-plan checks. It fails, and so emails, if a plan regresses or a query errors. It allows 150 ms a query, not the default 50: the server's cores are about half as fast as the development machine's (docs/server.md, section 5).
- **The app needs no restart after a load:** it reads the window for every new session, and its cache is keyed on it.

A task's runs and their output are on its page in Coolify. A failed run emails the team. Coolify disables a task after ten failures in a row; it shows that on the task.

## Deploy

**Automatically:** a merge to `main` builds and pushes the app image, then asks Coolify to deploy the app and the `jobs` container, each from the tag set on it in Coolify, `main`. The `jobs` deployment runs `migrate()` afterwards. The deploy step fails, and the run is red, if Coolify does not queue both.

**By hand:** in Coolify, the application's **Redeploy** button (**Deploy** while it is stopped). It pulls its tag, `main`, again.

**Roll back:** each merge also pushes `:<commit sha>`, with the commit's full 40-character sha (a short sha is not a tag). In Coolify, set the application's **Tag** (General → Image) to the last good commit's sha, and Redeploy. While the tag is pinned, every deployment of that application deploys that sha, CI's included: once CI has pushed the fix to `:main`, set the tag back to `main` and Redeploy. A migration cannot be undone this way: a release that changes the schema is fixed forward.

**Avoid restarting `prexp-jobs` between 02:00 and 05:00:** a restart is a full deployment, and it stops a running task.

## Rotate a password

For a role `prexp_<role>` (`owner`, `loader` or `app`):

1. **Change it in the database.** In `prexp-db`'s Terminal: `psql -U postgres -d prexp`, then `\password prexp_<role>`, which asks for the new password twice without showing it. Long, random, letters and digits only, as in server.md.
2. **Change it in Coolify,** in every resource that has the variable: always `prexp-db`, and `prexp-jobs` for the owner and the loader, or `prexp-app` for the app.
3. **Redeploy** `prexp-jobs` or `prexp-app`, whichever uses the role. Until then, connections already open keep working and new ones fail: the app stays up, but a lookup that needs a new connection fails. Its health check loads only the static page, so it does not notice. If the password in Coolify does not match the database's, the new container cannot start, and Coolify keeps the old one. `prexp-db` needs no restart: its variable is only read on the first start.

**The `postgres` superuser's password:** change it in the database first: in `prexp-db`'s Terminal, `psql -U postgres -d prexp`, then `\password postgres`. Then enter the same value on `prexp-db`'s General page (Credentials → Password) and save, so that Coolify's copy matches; no restart is needed. Changing it only on the General page changes nothing in PostgreSQL, which reads it only when it first creates its files: the old password would stay valid.

## Reload one month

In `prexp-jobs`'s Terminal:

```sh
nohup Rscript -e "prexp::load_month(202609)" > /data/epd/load_month.log 2>&1 &
tail -f /data/epd/load_month.log
```

The month is downloaded again, rebuilt beside the live data, checked, and swapped in. The app keeps serving the old data until the swap, a transaction of a few seconds. A month older than the window is refused before anything is downloaded.

## Rebuild from an empty database

The database is not backed up: everything in it comes from the portal, so it is rebuilt instead. Measured on the server on 25 November 2026: **64 minutes** for the twelve months, about 5 minutes a month, most of it building and checking each month; on four of the development machine's CPUs, 38 minutes ([docs/benchmarks.md](benchmarks.md)).

1. **Empty it.** In Coolify, stop `prexp-db`; the stop removes its container. Then, in Coolify's Terminal on the server itself (Terminal → the server, not a container), delete its data volume: `docker volume rm postgres-data-<db-id>`. This deletes all its data, for good. When `prexp-db` starts in step 2, Coolify creates the volume again, empty.

   **Never use Persistent Storage → Delete for this.** It only makes Coolify forget the volume, never adds it back, and leaves the data on the disk: the database would then start on a new, unnamed volume each time, empty after every restart.

   Or create a new database resource, as in server.md, section 1, named `prexp-db`. Its internal host name, `<db-id>`, is then new: set `PREXP_DB_HOST` to it on `prexp-jobs` and `prexp-app` before step 3, and redeploy `prexp-app` after step 3. Then delete the old database resource from its Danger Zone, with its volumes.
2. **Start `prexp-db`.** The initialization scripts run on the empty volume and create the roles and the database: check its log, as in server.md.
3. **Deploy `prexp-jobs`.** Its post-deployment command, `migrate()`, creates the schema.
4. **Load the window,** in `prexp-jobs`'s Terminal:

   ```sh
   nohup Rscript -e "prexp::load_window()" > /data/epd/load_window.log 2>&1 &
   tail -f /data/epd/load_window.log
   ```

   It loads the twelve most recent published months, oldest first. Stopped, it carries on where it left off when started again.
5. **Check:** `Rscript -e "prexp::check_plans(max_ms = 150)"`: every check must pass. Like the nightly check, it allows 150 ms a query; at the default 50 ms, two checks fail on time on this server.

With the same database resource, the app needs no redeploy: it shows "No months are loaded yet" until the first month is in, then the window as it grows.

**Drilled** on 25 November 2026, on a fresh database on the development machine's test server, with the thirteen fixture months in place of the portal's: `migrate()`, the thirteen loads (the first month left the window when the thirteenth came in, as in production), and `check_plans()` with all 25 checks passing, in 11 s. The app's window then read October 2025 to September 2026.

## When something goes wrong

**A failed scheduled task** (an email). Open the task's last run in Coolify (`prexp-jobs` → Scheduled Tasks → the task):
- "password authentication failed": a password differs between Coolify and the database. See "Rotate a password".
- "Another load is running on this database": a manual load overlapped the task. Let it finish; the next day's run catches up.
- "Checking the loaded months against the portal failed", or a download error: the portal was unreachable. The next run tries again; months already loaded stay live.
- A failed plan check (nightly): the run's output has the table of all 25 checks, and names each failure and why. To run it again in the Terminal: `Rscript -e "prexp::check_plans(max_ms = 150)"`.

Then run the command by hand in `prexp-jobs`'s Terminal, or with the task's "Execute now", to confirm the fix.

**The disk filled during a load.** The month being loaded is lost, never the live data: nothing changes before the swap. The load is recorded as failed, or, if the database stopped, when the next load starts: PostgreSQL can shut down when it cannot write its log, so if `prexp-db` is not running, read its log, free space, and start it again. Free space with Coolify → Servers → the server → Docker Cleanup, leaving volumes alone, and check the disk with `df -h` in Coolify's Terminal on the server. A load that failed after staging keeps the month's ZIP, about 0.7 GB, in `/data/epd`, and the next load of that month uses it: `ls -la /data/epd` in `prexp-jobs`'s Terminal shows it, and deleting it frees the space. Then load the month again.

**A failed swap.** The swap is one transaction: when it fails, it rolls back and the month is as it was before, with `failed` in `core.load_log`. "waited too long for a lock" means the app held a lock the swap needed; the swap retries itself, and a failure after the retries is fixed by loading the month again, at a quieter time.

**A stuck lock.** A load holds the advisory lock `(1886545272, 2)` for its session, and migrations `(1886545272, 1)`; both go when the session ends, even if the process died. If a load says another is running and none is, find the session in `prexp-db`'s Terminal:

```sh
psql -U postgres -d prexp -c "SELECT pid, usename, state, query_start, left(query, 60) FROM pg_stat_activity WHERE pid IN (SELECT pid FROM pg_locks WHERE locktype = 'advisory')"
```

and end it with `SELECT pg_terminate_backend(<pid>)`. A load that was cut short is recorded as failed when the next one starts.

**The app is down.** Coolify restarts a container that stops, and rolls back a deployment whose health check fails within about a minute. Look at `prexp-app`'s Logs. "The app must connect read-only" at start-up means it was given a login that can write: it must have the app role's only.
